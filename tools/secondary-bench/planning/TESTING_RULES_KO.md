# 공통 테스트·성능 측정·재테스트 지침

**문서 ID: SFINDER-TEST-001 / 버전: 2.0 / 발효: 2026-10-05**

이 문서는 앞으로 수행할 테스트의 공통 규칙이다. **목적에 따라 재테스트 대상을 구분하고, 테스트 횟수는 협의 후 실행 전에 확정한다.** 과거 캠페인에는 당시 동결한 지침·manifest를 적용한다.

v2.0 변경: A/B 성능 비교와 단순 성능 정보 수집의 재테스트 규칙 분리, 일률적인 4쌍/10쌍·5 runner 배치 해제, 목적별 횟수 협의, 종료한 A0 연구의 개별 지시 분리. 기존 v1.1은 [원문 스냅샷](testing-rules-history/TESTING_RULES_KO.v1.1.md)에 byte 그대로 보존했다. 스냅샷의 실행 지시는 역사 기록이다.

## 1. 먼저 테스트 목적을 정한다

| 목적 | 확인할 것 | 재테스트 대상 |
|---|---|---|
| 정확성·회귀 | 결과·계약·최적성·취소·회수 | 실패 원인에 맞는 검사. 성능 반복으로 증명을 대신하지 않음 |
| 단순 성능 정보 수집·진단 | 엔진별 시간·비용·변동·상태 기록 | 같은 조건의 `최대시간/최소시간 ≥ 1.10` |
| A/B 성능 비교 벤치마크 | 기준 대비 후보의 개선·악화와 기존 gate 영향 | 개선 폭 상위 10% ∪ 악화 폭 상위 10% ∪ 변동 ≥ 1.10 ∪ gate 영향 입력 |

- 3엔진의 광범위 성능 지도를 만드는 초기 측정은 **성능 정보 수집**으로 계획할 수 있다. 이후 현행 Auto와 후보 정책을 비교하는 실험은 **A/B 성능 비교**다.
- 엔진이 여러 개라는 이유만으로 정보 수집에 A/B tail 규칙을 적용하지 않는다. 반대로 A/B 개선·gate 통과를 주장하는 실험을 정보 수집으로 이름만 바꾸지 않는다.
- 한 캠페인에 목적이 여러 개면 단계별 대상·측정 계약·재테스트 규칙을 구분한다.
- `Actions success`, `harness/audit PASS`, `correctness PASS`, `performance PASS`, `제품 적용 결정`은 별도 상태다. 정보 수집 완료는 제품 성능 PASS가 아니다.

## 2. 실행 순서와 횟수 결정

```text
목적·질문 정의
  → 입력/fixture·기존 자료 확인
  → 최초 측정 및 재테스트 횟수·조건·예산 협의
  → manifest 동결
  → 최초 측정
  → 고정 규칙으로 재테스트 대상 산출·목록 고정
  → 별도 재테스트
  → 감사·해석·결정·보존
```

### 횟수는 목적별로 협의한다

- 최초 반복 수, 재테스트 반복 수, runner job 수·배치, warmup·대조 호출 수를 각각 정한다. **새 캠페인에 고정된 4회/10회 기본값은 없다.**
- A/B는 입력당 **쌍 수**로, 정보 수집은 입력×엔진×동일 조건당 **호출 수**로 적는다. “N회”만 써서 A/B 합계인지 각 variant 횟수인지 모호하게 하지 않는다.
- 변동 비율을 계산하려면 같은 조건의 유효 반복이 2개 이상 필요하다. 부족하면 `INSUFFICIENT_REPEATS`로 표시하고 안정적이라고 판정하지 않는다.
- 재테스트는 최초 측정과 분리한 추가 일정·원결과로 기록한다. 횟수를 채운 뒤 결과가 모호하다고 임의로 반복을 추가하지 않는다.
- Sol이 목적·비용에 맞는 횟수와 예산을 제안하고, 세션에서 협의해 확정한 값을 manifest에 기록한다. 미확정인 동안 하네스·fixture 준비와 경량 검사는 진행할 수 있다.

## 3. 재테스트 대상 선정 — 고정 규칙

### 3.1 공통 측정 단위

입력 ID뿐 아니라 엔진/variant, source·binary, 옵션·예산, lifecycle, 측정 경계가 같아야 같은 조건이다. 서로 다른 엔진 시간이나 cold/warm 시간을 섞어 변동을 계산하지 않는다.

- 개발/검증 분할, 모집단, 측정 경계, lifecycle별로 따로 선별한다.
- 같은 조건에서 runner 내부 및 runner 간/전체 `max(T)/min(T)`를 기록한다. 어느 쪽이든 1.10 이상이면 변동 대상으로 포함한다. 실제 runner 환경 차이도 함께 보존한다.
- 시간이 유효한 양수인지 확인한다. timeout 상한을 완료시간처럼 넣어 비율을 계산하지 않는다.
- 정상 bounded 실행은 그 계약 안에서 측정할 수 있다. exact 완료와 capped 상태를 섞어 같은 완료시간 분포로 취급하지 않는다.
- 필수 반복 누락·timeout·OOM·오류·증명 미확인은 별도 실패/미완료 원장에 남긴다(§5). 원장에 남긴 입력을 집계에서 조용히 삭제하지 않는다.

### 3.2 A/B 성능 비교

여기서 **A는 기준, B는 후보**이며 엔진이나 과거 빌드 이름과 무관하다.

입력 i, 사전에 지정한 pair j에 대해:

```text
q_ij = T_Bij / T_Aij
r_i  = median(q_ij)
개선: r_i < 1 / 악화: r_i > 1 / 변화 없음: r_i = 1
```

재테스트 대상은 다음 **네 집합의 합집합 S**다.

| 집합 | 선정 방법 |
|---|---|
| I10: 개선 폭 상위 10% | 개선군 I 중 `ceil(0.10 × |I|)`개. r_i가 작은 순 |
| W10: 악화 폭 상위 10% | 악화군 W 중 `ceil(0.10 × |W|)`개. r_i가 큰 순 |
| V: 변동 | A 또는 B의 같은 조건 반복에서 `max(T)/min(T) ≥ 1.10` |
| G: gate 영향 | 개선·악화가 기존 gate에 영향을 주는 입력. 아래 사전 선정 계약에 따름 |

`S = I10 ∪ W10 ∪ V ∪ G`. 여러 이유에 해당해도 입력을 중복 실행하지 않고 모든 선정 이유를 남긴다. 각 선정 입력은 A/B를 함께 재측정한다.

**상위 10%의 뜻**

- 분모는 개선군과 악화군 각각의 입력 수다. 가장 느린 입력 상위 10%나 10% 이상 개선된 입력을 뜻하지 않는다.
- 해당 군이 비어 있으면 0개, r_i=1은 양쪽에서 제외한다. 경계에 동률이 있으면 전부 포함한다.
- 결과를 본 뒤 임의 epsilon으로 작은 변화를 지우지 않는다. 상대 비율과 절대 ms 차이를 함께 보고한다.

**gate 영향 집합 G**

- 기존 gate의 수식·대상·경계와 G 선정 알고리즘을 최초 측정 전에 manifest에 고정한다. 악화뿐 아니라 개선으로 gate 판단에 영향을 주는 입력도 포함한다.
- 입력별 gate는 경계 통과·위반 등 해당 gate의 판정 규칙을 사용한다. 전체 sum/p95/CI 등 집계 gate는 경계·기여도·민감도를 어떻게 입력 목록으로 바꿀지 먼저 정한다. 단순한 “입력 ratio 위반”만으로 모든 집계 gate 영향을 대신하지 않는다.
- gate가 없으면 `G = ∅ (NO_GATE)`로 명시한다. 결과를 보고 새 gate를 만들어 재테스트 대상을 임의 선택하지 않는다.
- 규칙을 재현할 수 없으면 G 선정이 미완료다. Sol은 기존 gate와 후보 선정 방식을 제시해 협의 후 확정한다.

### 3.3 단순 성능 정보 수집·테스트

재테스트 대상은 **같은 조건의 `max(T)/min(T) ≥ 1.10`인 측정 항목**이다. 개선·악화 tail이나 A/B gate 영향 집합을 추가하지 않는다.

- 세 엔진 수집이면 엔진별로 변동을 계산한다. 예: 한 입력의 CP만 변동 기준을 넘으면 해당 입력×CP를 대상으로 식별한다.
- 변동 엔진만 재측정할지, 균형 있는 block을 위해 해당 입력의 세 엔진을 함께 재측정할지는 사전 일정에서 정한다. 추가 대조 호출을 필수 재테스트 선정 이유와 혼동하지 않는다.
- 수집 결과의 순위·시간 차이는 보고할 수 있지만, 그것만으로 새 정책의 분류·전환 비용이나 제품 gate 통과를 증명하지 않는다.

### 3.4 대상 고정과 대조군

- 최초 실행 전에는 **선정 규칙**을 고정하고, 최초 결과가 모이면 그 규칙으로 **대상 ID·모든 선정 이유·호출 일정**을 확정한다. 결과를 보고 편한 입력만 선택하지 않는다.
- 원자료 hash, 분석 버전, 선정 seed, 대상·제외/미완료 이유를 저장한다. 대상 목록 정렬은 matrixId/엔진 ID 등 고정 규칙을 사용한다.
- 선택 편향 확인용 비선정 대조군이나 동일 variant 환경 대조가 필요하면 선정법·횟수·비용을 사전에 별도로 정한다. 대조군은 위에서 정의한 필수 집합 S 또는 V 자체를 변경하지 않는다.

## 4. 측정 계약과 실행 환경

### 공정한 시간 비교

- A/B는 같은 runner와 lifecycle에서 시간상 인접한 pair로 실행하고 순서를 균형 배치한다. pair ID를 기록한다.
- 정보 수집은 입력×엔진 block과 반복 순서를 고정한다. 3엔진 block 자체를 사후에 임의의 A/B pair로 해석하지 않는다.
- 이전 자료에 pair ID가 없으면 순서만 보고 짝을 추정하지 않는다. 기존 `median(B)/median(A)` 등을 사용할 경우 `LEGACY_UNPAIRED`와 원래 계약을 명시하고 새 paired 자료와 구분한다.
- cold / compiled-module reuse / warm-instance를 분리한다. warm 결과로 cold 실패를 대신하지 않는다.
- setup, packing, native 준비, search, IPC, profile, 전환, cleanup을 가능한 범위에서 분리한다. 전체 응답시간은 그 경계를 직접 측정한다. 부분 median의 합은 전체 median이 아니다.
- secondary-only는 확보된 원본 행렬·K·seed를 재사용한다. 실제 명령 end-to-end에서는 열거·primary·대기·출력 비용도 포함한다.
- 계측/profile 실행은 비계측 성능과 별도 기록한다. 관측만 추가했다면 결과·states 보존과 계측 비용을 먼저 확인한다.
- wall/CPU/메모리의 측정 scope, 환경·PID/TID·도구 버전을 기록한다. 알 수 없는 값은 `UNOBSERVED`로 둔다.

### 어디서 실행하는가

- **로컬:** 경량 정확성·회귀, fixture/하네스 검사, 원자료 분석.
- **GitHub Actions:** 비교적 일정한 VM이 필요한 벤치마크와 연산량 있는 검사. `Qnia28/sfinder_wasm`의 별도 실험 branch에서 실행하며 원본 dev와 main은 변경하지 않는다.
- public 표준 runner를 사용한다. 현재 허용 병렬 한도는 **동시 VM 16개**이며 해당 작업의 여러 workflow를 합산한다. 한 비교 pair는 같은 VM에 둔다.
- runner job들이 물리적으로 다른 서버임을 보장하지 않으므로 “독립 runner job”이라고 기록한다. CPU 모델을 골라 재시도하거나 불리한 host 결과를 삭제하지 않는다.
- 동일 OS image·runtime·toolchain을 지정해도 CPU·주파수·배경 부하까지 같다고 가정하지 않는다. 실제 환경을 기록한다.

## 5. 정확성·실패 상태·재시도

### 정확성 계약

- 원본 weighted rows에서 K·coverage·quality를 독립 검산한다. 중복행 가중치·stable-ID universe·aliases를 유지한다.
- exact는 더 좋은 quality vector 부재와 같은 quality에서 더 우선하는 stable-ID 해 부재까지 증명해야 한다. 유효 witness나 반복 일치는 최적성 증명이 아니다.
- bounded probe, FEASIBLE, quality-only, proof pending을 exact로 바꾸지 않는다. 독립 oracle의 알고리즘·공유 코드 범위를 기록한다.
- 결정성 검사는 같은 엔진/설정의 selected IDs, quality vector, K, 완료 상태 및 보장되는 states를 비교한다. 서로 다른 엔진의 states 일치를 요구하지 않는다.
- 취소·buffer 소유권·Worker 회수·실패 fallback도 실제 사용 계약으로 검증한다.

### 결과 상태

`EXACT`, 정상 `CAPPED`, `TIMEOUT_*`, `OOM`, `ERROR`, `MISSING`, `PROOF_PENDING`, `MISMATCH`, `NOT_RUN_BUDGET` 등을 구별한다. 정상 capped는 정해진 bounded 호출의 정상 반환이지만 exact 완료는 아니다.

- 오류·timeout·누락은 자동 성능 재테스트로 숨기지 않는다. 완료 상태가 달라지거나 한 variant만 exact면 계약·증명 확인을 먼저 한다.
- 정확성 불일치·OOM·원자료 저장/protocol 오류는 관련 실행을 중단하고 원인을 확인한다. 미해결 입력을 performance-only PASS로 승인하지 않는다.

### 자율 교정과 재시도

- 누락 API 인자, 잘못된 경로, parser/IPC/업로드 등 교정 가능한 하네스 오류는 수정 → 경량 계약 검사 → source 재고정 → 미완료 호출 재시도로 처리할 수 있다. 단순 실수마다 별도 실패보고·봉인·사용자 승인을 반복할 필요는 없다.
- 같은 캠페인 origin·예산·입력·seed·K·state budget·측정 경계·gate·선정 규칙을 유지한다. 변하면 새 비교 계약으로 명시한다.
- 정상 완료한 측정은 새 값으로 교체하지 않는다. 검색 timeout·OOM·정확성 불일치·불리한 성능은 “단순 실수”가 아니다. 성공할 때까지 반복하거나 검색 상한을 자동 증액하지 않는다.

## 6. 실행 전 manifest에 기록할 것

| 구분 | 필수 내용 |
|---|---|
| 목적 | campaign ID, 지침 버전/hash, 질문·가설, 정보 수집/A·B 비교 구분, 종료 조건 |
| source | commit·WASM·도구 hash, Node/V8/Rust/browser, compiler flags, 실제 variant와 표시 label |
| 입력 | 원 bytes/hash, ID·aliases·mirror group, 노출·분할·선정/제외 사유, K 증명·seed·weighted rows·stable IDs |
| 측정 | 옵션·state budget·lifecycle·측정 경계, 반복·warmup·runner/block/pair·순서 |
| 재테스트 | 목적별 선정 규칙, gate와 G 알고리즘(없으면 NO_GATE), 협의한 반복·대조·배치·최대 호출 수 |
| 통계 | 비율·quantile·CI 수식, seed/단위, 결측·censoring·환경 경보 처리 |
| 자원 | call별 phase deadline·회수 제한, 메모리·동시 VM·총 job 수·wall/runner-hour/artifact 예산 |
| 보존 | 원결과 writer/ACK, 검산기, 원자료·실패 원장·source bundle·run/job ID·seal 위치 |

재테스트 대상 수가 사전에 정해지지 않으므로 동률 확장·변동군·대조군을 포함한 최악 호출 수를 계산하거나, 사전 합의한 단계별 예산 처리 방식을 명시한다.

호출 수 표기 예:

- A/B 최초 n쌍: 입력당 `2n` 호출. 재테스트 m쌍: 선정 입력당 추가 `2m` 호출.
- 정보 수집 최초 n회: 입력×엔진×조건당 n 호출. 재테스트 m회: 선정 항목당 추가 m 호출.
- warmup·환경 대조·정확성 oracle·fixture 추출·회수 비용은 별도 가산한다. n과 m은 협의할 변수이며 기본값이 아니다.

## 7. 예산·deadline·원자료 저장

- child 메모리 3GiB/swap 0을 기존 기본 제약으로 유지한다. 공통 상한 wall 3h/64 runner-hours는 캠페인마다 자동 부여되는 예산이 아니며 실제 계획에서 총량·origin을 명시한다. 변경은 실행 전에 협의한다.
- workflow 재시작으로 같은 캠페인의 시계·소비 예산이 초기화되지 않는다. 남은 예산이 다음 호출의 최악 상한보다 작으면 `NOT_RUN_BUDGET`으로 멈춘다.
- startup/API/search/process/audit/profile-export/durable-ACK/reap 등 필요한 timer를 독립 설정한다. 이전 호출 때문에 다음 입력의 비교 예산을 줄이지 않는다.
- solver와 독립된 watchdog/writer로 동기 WASM 정지·timeout을 처리한다. raw append/fsync/ACK 후 검산과 다음 호출을 수행한다. profile도 저장 ACK를 확인한다.
- 실행 중 대상·반복·상한을 좋은 결과가 나오는 방향으로 조정하지 않는다. 실패·취소·부분 artifact도 보존한다.

## 8. 결과 해석과 gate

- 최초 측정, 재테스트, 정확성 증명, 최종 판단을 각각 남긴다. 나쁜 원값만 새 값으로 교체해 sum/p95/CI PASS를 만들지 않는다.
- 재테스트 표본의 p95를 전체 모집단 p95로 확대하지 않는다. 전체 gate를 다시 확인하려면 고정된 전체 대상의 별도 확인 계획이 필요하다.
- 입력별 모든 호출/쌍비율, 절대 ms 차이, runner별 결과, max/min, 완료 상태, CPU·메모리를 함께 보고한다. 일부 완료한 표본만으로 확정 판정하지 않는다.
- “방향 재현”에 필요한 반복·runner 수·판정식을 실험 계획에 정한다. 과거의 “10쌍, 5 runner 중 4개” 규칙을 새 횟수에 자동 적용하지 않는다.
- 환경 민감성, 미확인, 증명 대기, 불일치를 개선/악화 판정과 구분한다. 작은 변화가 반복돼도 통계적 확정을 과장하지 않는다.
- 기본 quantile은 nearest rank `sorted[ceil(p*n)-1]`, 짝수 median은 가운데 두 값의 평균이다. paired 비율 median과 `sum(입력별 median B)/sum(입력별 median A)`는 다른 지표다.
- CI/재표집을 사용하면 seed·PRNG·입력 순서·runner 및 mirror group 단위를 고정한다. 관련 입력이나 같은 runner 반복을 독립 host 표본처럼 세지 않는다.
- 과거 A0 등 개별 캠페인의 gate는 당시 manifest에 속한다. 새 실험으로 자동 복사하거나 이 문서로 소급 변경하지 않는다.

## 9. 문서·자료 보존

- 필수 자료: PLAN/MANIFEST, SOURCE_LOCK, INPUTS/SELECTION, SCHEDULE, raw·실패 원장, 환경, AUDIT, ANALYSIS, RESULT, DECISION, source bundle/원격 commit, seal. 목적에 맞게 통합할 수 있으나 정보는 남긴다.
- 원 artifact byte/hash를 보존한다. 정렬·포맷 정리로 원 JSON을 덮어쓰지 않는다. parser 수정은 새 분석 버전으로 처리하고 불필요한 native 재실행을 피한다.
- 노출된 reserved 입력은 regression 자료다. 이름만 reserved인 입력을 fresh holdout이라고 부르지 않는다.
- 공통 지침은 새 버전으로 갱신하고, 실행마다 그때의 복사본/hash를 고정한다. 과거 봉인 자료·절대경로·manifest는 수정하지 않는다.
- 종료한 연구의 개별 실행 순서는 현재 작업 지시가 아니다. 현재 과제·역할은 [3체제 로드맵](../../THREE_ENGINE_ROADMAP_KO.md)을 따른다. Astra/Sol은 세션 내 전환으로 사용하며 서브에이전트를 생성하지 않는다.
